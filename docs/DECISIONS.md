# Decisions log

One paragraph per decision: context, decision, alternatives. Newest first.

## 2026-11-20 — "Coming soon" pages instead of 404s for unbuilt routes

**Context:** the header links to `/impact` and `/news`, and the footer to `/id`, none of which exist yet (T3.8, T3.4 and the ID card task are still open), so visitors hit a bare 404. **Decision:** a shared `InfoPanel` (`src/components/sections/InfoPanel.tsx`) renders a tinted "Bientôt disponible / Coming soon / قريباً" page for those three routes (`ComingSoon`), marked `noindex` so placeholders don't get indexed, with translations in the `comingSoon` namespace. The same panel styles a designed not-found page (`src/app/[locale]/not-found.tsx` for `notFound()` calls). Because this app has multiple root layouts and a top-level `[locale]` segment, URLs that match no route at all never reach that file — for those, `experimental.globalNotFound` plus `src/app/global-not-found.tsx` renders a trilingual (fr/en/ar) 404 that carries its own fonts and styles, since it bypasses all layouts and has no locale context. **Trade-off:** `globalNotFound` is experimental in Next 16; if it ever breaks on an upgrade, delete the flag and that one file and unknown URLs fall back to Next's default 404 — nothing else depends on it. **Not done:** the real Impact, News and ID card pages — the coming-soon pages are placeholders, and the components for real figures (`StatsBand`, `FlagshipActions`) already exist for T3.8.

## 2026-11-20 — Light-only redesign modelled on alan.com (supersedes the earlier "warm/orange" pass)

**Context:** the first redesign (Outfit headings, cream + orange CTA, dark-mode override) was rejected as "still shit"; the user asked for a light theme that mimics alan.com and for real figures and images. Alan's real stylesheet (fetched directly) shows white/`#fafafa` backgrounds, `#282830` text, indigo `#5c59f3` brand with mint `#22e39e` and pastel tint blocks, 24px card radii, very soft shadows, and medium-weight (500) balanced headlines in a custom sans. **Decision:** `src/styles/tokens.css` is now light-only (`color-scheme: light`, no `prefers-color-scheme: dark` block) with an Alan-like placeholder palette — still `TODO(board)`, swap the values once the board picks real brand colors; one family, Figtree (free, closest match to Alan's proprietary sans — we do not use their font, logo or mascot) plus Cairo for Arabic; headings are medium weight via one global `h1–h6` rule instead of per-component bolding; buttons are 12px-radius with an indigo primary and a mint `accent` variant for the CTA band. Home page: hero with photo and floating real-stat cards, tinted stat tiles, photo pôle cards, a flagship-actions figures section, projects, and a closing CTA band. **Figures** come only from the seed data (annual report 2026) — nothing invented. **Images** are Wikimedia Commons placeholders chosen to be Moroccan, licence-clear and **people-free** (Casablanca skyline, Al Haouz and Imlil landscapes, Fès ceramics); an argan-cooperative photo was rejected because it shows identifiable women and would imply a link to a JLM project, and photos of children were avoided given the open consent question (`docs/OPEN_QUESTIONS.md` #7). Credits live in `public/images/site/CREDITS.md`, `src/lib/content/site-images.ts`, and a footer line (required by CC BY-SA). **Alternatives considered:** hotlinking Unsplash/Pexels — rejected (Unsplash search is behind a bot challenge, and hotlinking is fragile); cloning Alan's exact palette/typeface — rejected as unnecessary and not ours to copy. **Known gap:** the header links to `/impact` and `/news`, which 404 until T3.8/T3.4 are built.

## 2026-11-20 — Three bugs found by actually running the stack for the first time

**Context:** every previous handover note admitted nothing in this repo had been run against real or emulated data. Setting up Firebase emulators (Firestore on a non-default port — 8080 was already taken by an unrelated local service, so `firebase.json` now points it at 8081) plus `pnpm seed` and a live `pnpm dev` to test the Stripe integration surfaced three genuine, pre-existing bugs, not anything this session introduced:

1. **`pnpm seed` and `pnpm make-admin` could never run.** Both import `src/lib/firebase/admin.ts` directly via `tsx`, which has `import "server-only"` at the top — but the `server-only` package wasn't an installed dependency at all (`pnpm add server-only` fixed that), and more fundamentally, that package unconditionally throws when imported outside Next's own build (it only works because Next's bundler special-cases and strips it). **Decision:** drop the `server-only` guard from `admin.ts` specifically — it's the Admin SDK bootstrap, which can't run client-side anyway (firebase-admin needs Node built-ins no browser bundle can resolve), so the guard was never adding real protection there, only breaking the scripts that need to import it directly. Every other file in `src/lib` keeps the guard.
2. **Every pledge submission would have crashed with a 500** (`Cannot use "undefined" as a Firestore value`) the moment any optional field (donor name on an anonymous pledge, a missing cover image, etc.) was left blank — the Admin SDK rejects `undefined` in a write payload unless `ignoreUndefinedProperties` is set, and this project's schemas produce `undefined` for essentially every optional field. **Decision:** set `ignoreUndefinedProperties: true` once in `getAdminDb()` (`src/lib/firebase/admin.ts`), covering this and the same pattern in today's new admin CRUD writes (project cover, platform screenshot, campaign cover, settings optionals, etc.) in one place instead of `?? null`-ing every optional field at every call site.
3. **That fix has an ordering trap under Turbopack's dev hot-reload specifically** (not a production concern): `.settings()` must be the very first call ever made on a Firestore client, but Turbopack resets the module's local `_db` binding to `undefined` on every file edit while the underlying client — cached by the Admin SDK against the Admin App singleton, which does survive the reload — stays the same object. A `.settings()` call after that object has already been used throws "already been initialized" permanently for the rest of that dev server process's life. **Decision:** wrap the `.settings()` call in a try/catch that swallows exactly that error; harmless in production where it only ever runs once. The practical lesson for next time: if a fresh fix to `admin.ts` ever stops taking effect in `pnpm dev`, stop and restart the dev server rather than relying on hot-reload.

## 2026-11-20 — Admin CRUD for Posts/Campaigns/Projects/Platforms/Settings (T3.6)

**Context:** `docs/HANDOVER.md` flagged this as the biggest remaining T3.6 gap — only auth and the Pledges table existed. The full AC (`JLM_PHASE3_DEMO_EXECUTION_PLAN.md` T3.6) also asks for a `LocalizedField` with FR/AR/EN tabs, autosave, and an image uploader with mandatory alt text. **Decision:** build real, working CRUD for all five entities using plain `<form action={serverAction}>` + React 19's `useActionState` (`src/components/admin/AdminForm.tsx`) for inline validation errors, and a shared `LocalizedField` (`src/components/admin/LocalizedField.tsx`) for fr/ar/en text fields — but skip autosave, preview, and the image uploader for this pass; image fields stay plain URL text inputs (same representation as the seed data), and nested array-of-object fields (campaign `breakdown`, project `stats`/`leads`) are edited as a raw JSON textarea rather than a dynamic repeater UI. Role enforcement follows the master plan's Section 5.1 matrix (`editor` writes posts/projects/platforms; `admin` only for campaigns/settings), checked both in each Server Action (`src/lib/security/require-role.ts`) and by redirecting the wrong role away from the page — consistent with the existing Pledges page's `redirect("/admin")` pattern, not the dedicated "403 screen" the day-by-day plan's AC literally asks for. Every write now sets `updatedBy`/`updatedAt` (added to the `project`/`platform`/`post`/`campaign`/`settings` schemas) to satisfy the "every write logs the author" AC. **Alternative considered:** a generic schema-driven form builder — rejected as premature abstraction for 5 entities with genuinely different field shapes; the repetition between the 4 content forms is small and each is easier to read written out. **Still open, not done here:** image uploader, autosave/preview, the dedicated 403 screen, and CRUD for the smaller entities the write-matrix also names (stats, flagship actions, team, partners, users) — see `docs/HANDOVER.md`.

## 2026-11-20 — Stripe test-mode card payment added ahead of the frozen Gate 3 scope

**Context:** `docs/BACKLOG.md` lists online card payment as release 2 (out of scope before Gate 3) because it needs a real merchant account the board hasn't set up, and `docs/OPEN_QUESTIONS.md` records that Stripe does not pay out to Moroccan bank accounts — the real local option is CMI, which needs a bank merchant contract, not a free signup. The user explicitly asked for a payment gateway "using some free tool" anyway, so this is a deliberate exception to the frozen scope for this one item, not autonomous scope creep. **Decision:** add Stripe Checkout as a second pledge payment method, test-mode only, entirely gated on `STRIPE_SECRET_KEY` being set (`src/lib/payments/stripe.ts`); with no key configured the site behaves exactly as before (bank-transfer pledges only). A card pledge is created in Firestore the same way as a bank-transfer one (`status: "pledged"`), then redirected to a Stripe-hosted Checkout Session (`src/app/api/pledges/route.ts`); `src/app/api/webhooks/stripe/route.ts` verifies the `checkout.session.completed` webhook and flips the pledge to `"received"`. No real money can move through this: it only works with Stripe test keys, and nothing here constitutes the real payment gateway the board still needs to set up for launch. **Alternative considered:** PayPal (does support Moroccan payouts, more realistic long-term) or scaffolding CMI directly — rejected for now because Stripe's test mode and docs are the fastest free path to a working demo; swapping providers later is a config/route change, not a redesign, since the pledge schema's `paymentMethod`/`paymentProvider` fields aren't Stripe-specific.

## 2026-11-19 — Next.js 16 breaking changes

**Context:** `create-next-app@latest` installed Next.js 16.4.6, which the framework's own `AGENTS.md` flags as having breaking changes versus older training data. **Decision:** (1) `middleware.ts` is renamed `proxy.ts` and exports a `proxy` function — `src/proxy.ts` wraps `next-intl`'s middleware and re-exports it under that name. (2) There is no single `app/layout.tsx`; per Next's "multiple root layouts" convention, `src/app/[locale]/layout.tsx` and `src/app/admin/layout.tsx` are each their own root layout (each defines its own `<html>`/`<body>`), which is also how the master plan's locale-prefixed public site and non-localized `/admin` can have different `lang`/`dir` without one layout fighting the other. (3) Disabled the `cacheComponents`/`partialPrefetching` experimental flags that `create-next-app` turned on by default — they require wrapping every dynamic data read in Suspense or `"use cache"`, which is a different data-fetching model than the plan assumes (plain ISR + `revalidateTag` from `/api/revalidate`, Section 8.3). **Alternative considered:** adopt Cache Components now — rejected as unnecessary complexity for a 3-week build with a different intended caching model already specified.

## 2026-11-19 — CSS logical-property lint simplified

**Context:** the master plan (Section 3) asks for "a lint rule (stylelint or ESLint plugin for Tailwind)" forbidding physical CSS properties, to protect RTL (risk #5 in the register). A full custom stylelint/ESLint plugin is significant setup for a Tailwind-v4 project where almost all spacing is utility classes, not raw CSS. **Decision:** `scripts/check-logical-properties.ts`, run via `pnpm lint:logical` and wired into CI, greps `src/**/*.{ts,tsx,css}` for forbidden physical patterns (`ml-`, `mr-`, `pl-`, `pr-`, `left-`, `right-`, `text-left`, `text-right`, `margin-left`, etc.) and fails with file:line on a match. **Alternative considered:** `stylelint-use-logical` — left as a follow-up if the team wants stricter raw-CSS coverage later; logged in `docs/BACKLOG.md`.

## 2026-11-19 — Dropped `unstable_cache` around Firestore reads

**Context:** wrapping the content-layer Firestore reads (`src/lib/content/cache.ts`, `settings.ts`) in `next/cache`'s `unstable_cache` reproducibly crashed `pnpm dev` with `Error: Expected a suspended thenable. This is a bug in React.` as soon as a component using `next-intl`'s RSC hooks (`useTranslations`/`useLocale`) also awaited one of these cached reads — confirmed by removing `unstable_cache` and watching the crash disappear. This looks like a Next.js 16 / Turbopack / next-intl interaction bug, not something wrong in our code. **Decision:** read Firestore directly (plain `async` functions, no `unstable_cache`), and get "publish shows up within a minute" (Section 8.3's AC) from `/api/revalidate` calling `revalidatePath`/`revalidateTag` plus Next's normal per-request fetch instead. **Alternative considered:** pin an older Next.js 16 patch version or next-intl version — not attempted yet; revisit if this turns out to be a known, fixed upstream bug.

## 2026-11-19 — Reference-code generator (risk #7)

**Context:** register risk #7 requires the pledge reference generator to be collision-proof by design, not caught later. **Decision:** `JLM-{year}-{4 chars from a 32-symbol unambiguous alphabet}` (`ABCDEFGHJKMNPQRSTUVWXYZ23456789` — no `0/O/1/I/L`) gives 32⁴ ≈ 1.05M combinations per year; `generatePledgeReference` in `src/lib/validation/reference.ts` checks the candidate against Firestore and retries (bounded, throws after 10 attempts) rather than trusting entropy alone. Covered by a Vitest unit test asserting no collisions are produced against a mocked existing set.
